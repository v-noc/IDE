# 06 · Tracking Functions and Classes

To make logs, tests, playgrounds, and documents stick to a **symbol** rather than a **line number**, V-NOC needs every function and class to have a **stable identity**. That identity has to survive renames, refactors, moves between files, and re-formatting.

This page explains how V-NOC achieves that and how to consume it from your own code.

---

## The problem with line numbers and paths

The naive ways to identify a function are all fragile:

| Approach | Breaks when |
|---|---|
| File path + line number | You add or remove a line above it |
| Fully-qualified name | You rename the function or move the file |
| AST position | The formatter reorganises whitespace |

A graph database wants something **persistent**. So V-NOC injects an ID directly into the source.

---

## How V-NOC tracks symbols

When the parser first sees a function or class, the language driver injects a **stable UUID** into the source file and remembers it in the graph.

For Python, the marker lives in the docstring:

```python
def my_function(arg1, arg2):
    """ ID: 7b1d9c8e-23a8-4f64-8b2a-9d6cf5b95812 """
    # your code
    return ...
```

For TS/JS, the marker lives in a comment immediately above the symbol (driver-specific, see `src/lsp/ts_js/src/driver/`).

**Once the ID is in the source, it never changes.** Subsequent re-parses look the ID up, find the matching graph node, and update its location instead of creating a new one.

### Where this happens

| Layer | File | Role |
|---|---|---|
| Python driver | `src/lsp/py/vnoc_lsp_python/id_injector.py` | Rewrites source with `LibCST` to add `""" ID: <uuid> """` to functions and classes that don't have one |
| Python driver | `src/lsp/py/vnoc_lsp_python/file_folder_ids.py` | Same idea, for file- and folder-level IDs |
| TS/JS driver | `src/lsp/ts_js/src/driver/` | The ts-morph equivalent |
| Backend orchestrator | `src/backend/app/core/parser/graph_builder/orchestrator.py` | Calls `read_or_inject_*` before parsing |

The driver returns the `modified` flag so the backend knows whether to write the file back to disk.

---

## What gets a stable ID

- **Functions** (top-level and nested)
- **Methods** (instance, class, static)
- **Classes**
- **Files** — `file_id` lives in a header comment
- **Folders** — `folder_id` lives in a sentinel file at the folder root

Anonymous lambdas, expression-bodied arrows, and synthesised dunder methods are **not** ID-injected; they appear as ephemeral nodes in the graph and disappear if the source changes.

## Consuming the IDs in your own code

If you decorate functions with `vn-logger`, the function must reference its V-NOC ID:

```python
from vn_logger import configure_logger, context_logger

configure_logger("http://localhost:8050/api/v1/jsonrpc", "your-project-id")

@context_logger(function_id="7b1d9c8e-23a8-4f64-8b2a-9d6cf5b95812")
def my_function(arg1, arg2):
    """ ID: 7b1d9c8e-23a8-4f64-8b2a-9d6cf5b95812 """
    return arg1 + arg2
```

The `function_id` argument to `@context_logger` is the same UUID the parser injected. The decorator emits structured events tagged with that ID, and V-NOC attaches them straight to the matching node.

For the full logger walkthrough see `07-logs.md`.

## Why the docstring?

Three reasons:

1. **Visible.** A developer reading the file sees the ID. There is no hidden sidecar database for them to lose.
2. **Formatter-safe.** `black`, `prettier`, and friends preserve docstrings and leading comments.
3. **Tooling-friendly.** Stack traces show the docstring, agents see it, code reviews see it.

The downside is a few extra lines per symbol. We've judged that to be worth it — a graph is only as good as its keys.

---

## What happens on rename or move

| Event | What V-NOC does |
|---|---|
| You rename `my_function` → `my_thing` | The ID stays. The node's `name` field updates. All edges (calls, logs, tests) follow. |
| You move it to another file | The ID stays. The node's `file` edge updates. |
| You copy-paste it elsewhere | The ID exists in two places. The driver detects the duplicate and re-injects a fresh ID into the copy. |
| You delete the ID by hand | The driver re-injects a new one. The old graph node becomes orphaned and is GC'd. |

---

## Common questions

**Won't this pollute git diffs?** Only on the first parse. After that, the ID is part of the file like any other constant.

**Can I disable it?** Not today — IDs are how V-NOC works. You can format / hide them in your editor.

**What about generated code?** The parser ignores files marked generated (e.g. `# generated by …` headers) and skips ID injection there.
